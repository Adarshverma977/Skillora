# Skillora — Database Schema Design

## 1. Overview

Skillora uses MongoDB as its database and Mongoose to define models, validate documents, and perform database operations.

The primary collections documented for the application are:

1. `users`
2. `learningentries`

The relationship between these collections is one-to-many: a user can own multiple learning entries, and each learning entry is associated with its owner.

This document describes the known data model and its integrity requirements. Exact field definitions, defaults, indexes, and schema options must be confirmed against the current Mongoose model files.

## 2. Users Collection

**Collection:** `users`

The User model stores student account information, authentication-related data, email-verification state, and profile information.

### 2.1 Document Fields

| Field | Expected Type | Purpose |
|---|---|---|
| `_id` | ObjectId | Unique user identifier generated by MongoDB |
| `name` | String | Student's display name |
| `email` | String | Account email used for authentication |
| `password` | String | Hashed password |
| `isEmailVerified` | Boolean | Email-verification state |
| `profilePhoto` | String | Profile-image URL or storage reference, if configured |
| `createdAt` | Date | Account creation timestamp, if timestamps are enabled |
| `updatedAt` | Date | Last document update timestamp, if timestamps are enabled |

The table describes the intended field roles. Field names, required constraints, defaults, normalization behavior, and timestamp configuration must match `server/src/models/User.js`.

### 2.2 Validation and Integrity Requirements

- Account email addresses must be validated and normalized consistently.
- Email uniqueness must be enforced through the database schema or an appropriate unique index.
- Passwords must be hashed before persistence.
- Plaintext passwords must never be stored.
- Email-verification state must be managed by the authentication workflow.
- Profile-image references must be validated according to the implemented upload mechanism.
- Schema-level validation and API-level validation should work together.

### 2.3 Authentication-Related Data

Email verification and password recovery require secure token handling.

The exact token fields, expiry rules, storage strategy, and invalidation behavior must be documented from the current User model and authentication services rather than inferred from the feature names.

Password hashes and other sensitive authentication fields must not be exposed in ordinary user-profile responses.

## 3. Learning Entries Collection

**Collection:** `learningentries`

The LearningEntry model stores individual learning-journal records belonging to students.

### 3.1 Document Fields

| Field | Expected Type | Purpose |
|---|---|---|
| `_id` | ObjectId | Unique learning-entry identifier |
| `user` | ObjectId reference | Identifies the owning user |
| `topic` | String | Name of the learning topic |
| `description` | String | Description of the learning activity |
| `studyDurationMinutes` | Number | Duration of the study session in minutes |
| `difficulty` | String | Difficulty classification |
| `learningDate` | Date | Date associated with the learning activity, if present in the model |
| `createdAt` | Date | Entry creation timestamp, if timestamps are enabled |
| `updatedAt` | Date | Last document update timestamp, if timestamps are enabled |

The actual schema in `server/src/models/LearningEntry.js` is authoritative. Confirm optional fields, defaults, enumerated values, and timestamp settings before relying on every field listed above.

### 3.2 Validation and Integrity Requirements

- Each entry must be associated with its owner.
- Topic and description values must follow the implemented validation rules.
- Study duration must be a valid number within the application's accepted limits.
- Difficulty values must follow the values permitted by the model.
- Date fields, when present, must contain valid dates.
- Invalid document data must be rejected before it can corrupt application state.

The exact allowed difficulty values and numerical limits should be taken from the current schema and request-validation definitions.

## 4. Relationships

The relationship between users and learning entries is **one-to-many**.

```text
User
 │
 ├── Learning Entry 1
 ├── Learning Entry 2
 ├── Learning Entry 3
 └── Learning Entry N
```

Each learning entry stores the owning user's identifier in its `user` field.

### Ownership Rules

- Obtain the authenticated user's identity from the verified authentication context.
- Do not trust a client-provided user ID as proof of ownership.
- Scope private entry queries to the authenticated user.
- Check ownership before updating or deleting an entry.
- Prevent users from reading another user's entries by changing an entry identifier.
- Apply the same ownership restrictions to dashboard analytics and search results.

A valid MongoDB ObjectId identifies a document; it does not grant permission to access it.

## 5. Indexing Strategy

Indexes should support actual query patterns without introducing unnecessary write overhead.

### Users

A unique index on normalized email is appropriate if email is the unique account identifier.

The index definition and normalization strategy must be verified against the User model and database configuration.

### Learning Entries

Potential indexes to evaluate include:

| Candidate Index | Intended Use |
|---|---|
| `{ user: 1, createdAt: -1 }` | Retrieve a user's most recently created entries |
| `{ user: 1, learningDate: -1 }` | Retrieve a user's entries by learning date |
| `{ user: 1, difficulty: 1, learningDate: -1 }` | Filter entries by difficulty and date |

These are candidate indexes, not a claim that all of them are currently configured.

Before adding an index:

1. Inspect the existing schema and indexes.
2. Review the queries used by the API.
3. Evaluate whether the index supports those queries.
4. Check index size and write overhead.
5. Verify index creation and behavior in the target database.

Topic search may require a different indexing strategy depending on whether the implementation uses case-insensitive regular expressions, normalized fields, text indexes, or another search approach.

## 6. Dashboard and Analytics

Dashboard metrics are derived from the authenticated user's learning entries.

### 6.1 Total Entries

Count the learning entries belonging to the authenticated user.

### 6.2 Total Study Duration

Sum `studyDurationMinutes` across the user's relevant entries.

Convert the result into hours or hours and minutes for presentation. Keep the underlying calculation consistent in minutes.

### 6.3 Weekly Summary

Aggregate the user's learning activity over a clearly defined weekly period.

The implementation should define the date boundaries and timezone behavior consistently.

### 6.4 Recently Added Entries

Retrieve the user's latest entries using the appropriate creation or activity timestamp, according to the intended behavior.

### 6.5 Entry Analytics

The implemented analytics work includes support for average session duration and unique-topic counting.

Unique-topic calculations should normalize case and surrounding whitespace consistently where required.

### 6.6 Data Integrity

- Restrict aggregation pipelines to the authenticated user's records.
- Handle users with no entries.
- Avoid dividing by zero when calculating averages.
- Keep date boundaries and duration units consistent.
- Test analytics against representative datasets.

## 7. Data Integrity and Ownership

The database and API layers should work together to protect data integrity.

- Validate request data before database writes.
- Enforce Mongoose schema constraints.
- Prevent duplicate account emails through appropriate uniqueness enforcement.
- Validate identifiers before using them in database operations.
- Scope private data access to the authenticated owner.
- Avoid exposing password hashes and sensitive authentication fields.
- Handle missing documents and invalid references appropriately.
- Define account-deletion and related-data cleanup behavior before implementing permanent deletion.

A Mongoose reference alone does not automatically guarantee that the referenced user exists or that a requester is authorized to access the document.

## 8. Testing Considerations

Database-related tests should verify:

- Valid and invalid User documents.
- Valid and invalid LearningEntry documents.
- Required fields and permitted values.
- Email uniqueness behavior.
- Ownership restrictions on read, update, and delete operations.
- Correct dashboard aggregation results.
- Empty datasets and boundary conditions.
- Date filtering and duration calculations.
- Appropriate handling of invalid identifiers and missing records.

Run the relevant automated tests after changes to model definitions, indexes, validation rules, or aggregation pipelines.

## 9. Future Considerations

The schema may evolve as Skillora introduces additional requirements, such as:

- Learning tags and categories
- Learning streaks
- Study goals
- Reminders
- Additional progress analytics

Future schema changes should include a clear migration or compatibility strategy where necessary, updated documentation, and relevant tests.

## 10. Schema Status

Skillora has implemented the User and LearningEntry models and backend functionality for learning entries, analytics, and profile operations.

This document records the known data model and required integrity rules. The exact field definitions, defaults, indexes, and constraints must be cross-checked against the current model files before being treated as a complete schema reference.

Changes to the models should be reflected in this document and in any affected API, architecture, security, and testing documentation.
